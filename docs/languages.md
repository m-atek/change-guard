# Languages

The change guard's core check does not care which language a project uses: it runs the test command you give it on the head and on the base, reads the per-test report the runner writes, and links each base failure to the change. Since version 0.3.0 that core check has run for real on ten toolchains outside Python, on GitHub's hosted Linux runner. This page says what ran, how the guard reads each runner, and where the guard is weaker outside Python.

**The built-in probe exists for Python only.** For every other language in the table, the guard proves a change through the base run alone. That is enough when a change alters existing behaviour: the new test fails on the base by assertion, and the change passes as `ok`. It is not enough when a change adds a new function: on the base the new test fails only because the function does not exist yet (a compile error or a load error), which proves nothing about the test's assertions. Without a probe the guard cannot tell a test that only calls the new function from one that checks its result; both pass as `ok-unproven` (see "New functions without a probe" below).

## The seeded cases

Each fixture has a base commit with one function, `total(unit price, quantity)`, and its test, and five seeded changes. The results were the same in every row above:

1. A 10% bulk discount with no test: STOPPED (`no-test`).
2. The same discount with a new test that also passes without it: STOPPED (`test-passes-on-base`).
3. The same discount with a new test that checks it: PASSED (`ok`); the new test fails on the base by assertion.
4. A new function `formatPrice` with a test that only calls it and asserts nothing: PASSED (`ok-unproven`), note `probe-unavailable`.
5. The same new function with a test that checks its result: PASSED (`ok-unproven`), note `probe-unavailable`.
6. Cases 4 and 5 with `base_error_policy: "stop"`: STOPPED (`base-error-only`) both.

In case 4 and 5 the base run fails because `formatPrice` does not exist there, and the guard read that from the runner's own message: `TypeError: (0 , formatPrice) is not a function` (Vitest), `TypeError: formatPrice is not a function` (Jest), javac's `cannot find symbol` with `symbol: method formatPrice(int)` (Maven), `undefined: FormatPrice` (Go), `error CS0117: 'Pricing' does not contain a definition for 'FormatPrice'` (C#), `Error: Call to undefined method Shop\Pricing::formatPrice()` (PHPUnit) and `undefined method 'format_price' for module Shop::Pricing` (RSpec), javac's `cannot find symbol` through Gradle, `Unresolved reference 'formatPrice'` (Kotlin) and `error: type 'Pricing' has no member 'formatPrice'` (Swift, with XCTest and with Swift Testing). Each of these is classified as "new code is missing", never as proof. The captured reports and messages are in `tests/data/polyglot/` and the unit tests in `tests/test_polyglot_reports.py` read them.

## New functions without a probe

What the guard does today, outside Python, when a change adds a function and its test fails on the base only because that function is missing:

- With the default `base_error_policy` (`probe`), the change passes as PASSED `ok-unproven`. The sentence says what the guard could not show: "The new tests fail on the base only because the code they call is new in this change, and no probe ran, so the guard cannot show that they check its behaviour; a reviewer should read the assertions." The note `probe-unavailable` names the file types, the log's probe column says `unavailable`, and since 0.3.0 the GitHub annotation for `ok-unproven` is a warning, not a notice. It never says PASSED `ok`, which is kept for a base failure by assertion.
- With `base_error_policy: "stop"`, the same change is STOPPED `base-error-only`, and so is an honest change whose test does check the new function (case 5). Those changes then need the recorded skip step.
- A runner option that fails a test without any assertion stopped the call-only case on two runners: with PHPUnit's `--fail-on-risky` and with Vitest's `--expect.requireAssertions`, case 4 is STOPPED (`test-fails-on-head`) while case 5 still passes as `ok-unproven` (variants in run 44338193666). This only catches a test with no assertion at all; a test with a weak assertion (for example that the result is not null) still passes.
- `probe_command` lets you plug in your own mutation tool for these languages. It has not been tried with any real mutation tool.

The recommendation, until a probe exists for your language: keep the default and treat `ok-unproven` as "a reviewer reads the assertions of this pull request", or set `base_error_policy` to `stop` if you would rather skip honest new-function changes by hand than let a weak one through.

## How each runner differs

- **Vitest and Jest** name each test by the absolute path of its file. The head and the base run in different folders, so with the code of 0.2.2 no base result would have matched its head result (a unit test shows the ids differ; 0.2.2 itself was not run on these fixtures). 0.3.0 takes the worktree folder out of every test id and group. Vitest reports a missing import as `(0 , formatPrice) is not a function`, which the pattern of 0.2.2 did not recognise: in an earlier run of the workflow (run 44335953379, with the id fix but that pattern), Vitest's cases 4 and 5 passed as PASSED `ok`, the missing function counted as proof. 0.3.0 fixes the pattern and reads the error class of every Jest and Vitest failure (an assertion error, a matcher failure or an exception such as `TypeError`), so an exception is no longer reported as a failure "by assertion".
- **Maven** compiles every test source before it runs one, so a test file that does not compile on the base stops all of them, and Surefire writes no report. The guard then reads the end of Maven's output. `-Dtest` takes class names separated by commas, which the new placeholder `{classes_csv}` gives. It needs the standard `src/test/java/` layout to turn a file into a class name.
- **Go** runs whole packages: `{dirs}` runs every test in the folders of the changed test files, and a package that does not build on the base gives the same error to each of its tests, old ones included. Go's report does not name the file of a test, so the note "also passes on the base" is not given for Go.
- **.NET** cannot run one file: `{dotnet_filter}` selects the test classes named like the changed test files (`FullyQualifiedName~BulkTests` for `BulkTests.cs`), so each test class must be named like its file. When the tests do not compile on the base there is no TRX file and the guard reads the end of the output. On this runner `dotnet --version` showed SDK 11.0.100 although the workflow asked `setup-dotnet` for 10.0.x; the newest installed SDK built the `net10.0` projects.
- **PHPUnit** counts a test without assertions as risky but passed, and its JUnit log shows it as passed. `--fail-on-risky` changes that (above).
- **Gradle** compiles every test source before it runs one, like Maven, so a test that does not compile on the base leaves no XML results; the guard then reads the end of Gradle's output. `{gradle_tests}` gives one `--tests` per changed test class, from the standard `src/test/java/` or `src/test/kotlin/` layout. The fixtures switch the Gradle daemon off (`org.gradle.daemon=false`, `--no-daemon`) and run the Kotlin compiler inside Gradle (`kotlin.compiler.execution.strategy=in-process`): the guard ends every process a test run leaves behind, and a daemon that kept running could write into a worktree after the guard checked it (the daemon on was not tried). That costs a cold JVM per run, about 20 to 31 seconds per guard run here, which is why these fixtures set `time_budget_seconds` to 600. On this runner `java` on the path was 25.0.5, but Gradle ran on the Java 21.0.13 that `setup-java` put in `JAVA_HOME`.
- **Kotlin** reports a missing function as `Unresolved reference 'formatPrice'.` (the 2.x compiler, which quotes the name); the pattern also reads the older form without quotes. The function has to be in a class or `object` so the test calls it as `Pricing.formatPrice`; the guard's definition patterns read `fun` lines.
- **Swift**: on a developer Mac with Swift 6.4, `swift test` wrote the xUnit file for XCTest only with `--parallel` (without it, only the Swift Testing file), so the configuration has `--parallel`; the Linux runs used it and were not tried without it. XCTest's xUnit file says only `failure` for a failed assertion, without the values, so the per-test line has no detail; Swift Testing's says `Expectation failed: Pricing.total(1000, 10) == 9000`. `{names_regex}` (new in 0.3.0) selects the test classes or suites named like the changed test files for `--filter`. Each worktree builds the package from scratch, about 12 to 16 seconds per guard run here. The Swift compiler colours its messages even without a terminal; since 0.3.0 the guard takes the colour codes out of the line it shows.
- **RSpec** passes an example without expectations. Its JSON report names the exception class, so a `NoMethodError` is read as an error and linked to the change.

## Not verified

- Windows and macOS runners, and every CI platform other than GitHub Actions, for every language here.
- Other versions of these runners, and other runners: NUnit, MSTest, xUnit 3, Mocha, node's own test runner, Minitest, PHPUnit 10 and 12, Jest 30, Vitest 4, Gradle 8, the Gradle wrapper (`./gradlew`), Kotlin Multiplatform, Android projects, Gradle with the daemon on.
- Xcode projects, `xcodebuild` and every macOS runner; Swift on Windows.
- Monorepos and multi-module builds (several Maven modules, several .NET test projects, Go workspaces, npm workspaces).
- A probe for any language other than Python, and `probe_command` with a real mutation tool.
- Client code. Every run on this page is on a tiny demonstration project.
